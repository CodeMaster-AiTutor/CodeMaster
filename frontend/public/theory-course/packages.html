Packages

What is a Package?

A package is a folder that groups related Java classes together. It keeps large projects organized, avoids name conflicts, and helps access control.

Packages also define a namespace. Two classes can have the same name if they are in different packages.

Package-level access means members without public/private/protected are visible only inside the same package.

Think of packages as the address system for classes. The fully-qualified name (package + class name) uniquely identifies a class in a project or library.

Good package design groups classes that change together and separates classes that are used for different purposes.

  • Namespaces: prevent class name clashes across libraries and modules
  • Encapsulation: hide helper classes inside a package boundary
  • Structure: mirror your project’s domain in a clean hierarchy
com.myapp.models → Student.java, Teacher.java, Course.java com.myapp.utils → MathHelper.java, DateHelper.java com.myapp.database → DBConnection.java, QueryBuilder.java
  • Organization: structured navigation in large projects
  • Name conflicts: java.util.Date vs java.sql.Date
  • Access control: hide implementation within a package

Built‑in Java Packages

Java ships with many standard packages. java.lang is imported automatically, but most others require an explicit import.

Each package targets a specific area: utilities, I/O, networking, time, math, and more.

Knowing which package a class lives in helps you find documentation and avoid name conflicts.

  • java.lang: core language classes used in every program
  • java.util: collections, utilities, scanners, random, optional
  • java.io and java.nio: file and stream I/O
  • java.time: modern date/time API
  • java.net: sockets and HTTP clients
Package → What it contains java.lang → String, Math, System, Integer (auto‑imported) java.util → ArrayList, Scanner, HashMap, Collections, Arrays java.io → File, BufferedReader, FileWriter java.math → BigInteger, BigDecimal java.time → LocalDate, LocalTime java.net → URL, HttpURLConnection
Exam Point: Only java.lang is imported automatically.

The import Keyword

import tells the compiler where to find classes so you can use short names in code.

Wildcard imports include only classes in that package, not sub‑packages.

Imports are compile-time only. At runtime the JVM loads classes by their full package name.

If two classes have the same name, you must use the fully-qualified name to avoid ambiguity.

  • Explicit imports make code clearer and avoid name conflicts
  • Wildcard imports reduce typing but can hide conflicts
// import specific class import java.util.Scanner; import java.util.ArrayList; // import entire package import java.util.*; // does not include sub‑packages // no import (full name) java.util.Scanner sc = new java.util.Scanner(System.in);
Exam Point: import java.util.* does not import java.util.regex.*

Creating Your Own Package

The package statement must be the first line in the file, and the folder structure must match it.

When compiling from the command line, use javac -d to create the correct folder structure.

The folder layout must mirror the package name exactly or the compiler and JVM cannot find your classes.

IDE projects usually generate this structure for you, but it is important to understand the mapping.

  • package com.app.utils → src/com/app/utils/
  • package org.project.models → src/org/project/models/
package com.myapp.models; public class Student { private String name; private int age; public Student(String name, int age) { this.name = name; this.age = age; } public String getName() { return name; } public int getAge() { return age; } }
project/ └── src/ └── com/ └── myapp/ └── models/ └── Student.java

Package Naming Conventions

Package names use lowercase and typically follow reverse‑domain style.

This avoids clashes across projects and makes packages globally unique.

Short, meaningful subpackages indicate responsibility: model, service, util, db.

Avoid uppercase letters, underscores, or single-letter package names in real projects.

com.companyname.projectname.modulename com.google.gson org.apache.commons.lang com.fasterxml.jackson.core io.github.username.myproject
Exam Point: Reverse‑domain naming ensures global uniqueness.

Complete Multi‑Package Example

Each package focuses on a single responsibility. Import is used to connect them in the main app.

This structure keeps models, utilities, and entry points separate, which is easier to maintain.

As projects grow, you can add more packages without changing existing code structure.

StudentApp/ └── src/ ├── com/studentapp/models/ │ └── Student.java ├── com/studentapp/utils/ │ └── GradeCalculator.java └── com/studentapp/main/ └── Main.java
// Student.java package com.studentapp.models; public class Student { private String name; private int age; private double[] marks; public Student(String name, int age, double[] marks) { this.name = name; this.age = age; this.marks = marks; } public String getName() { return name; } public int getAge() { return age; } public double[] getMarks() { return marks; } @Override public String toString() { return "Student{name='" + name + "', age=" + age + "}"; } }
// GradeCalculator.java package com.studentapp.utils; public class GradeCalculator { public static double average(double[] marks) { double sum = 0; for (double m : marks) sum += m; return sum / marks.length; } public static String grade(double average) { if (average >= 90) return "A"; else if (average >= 75) return "B"; else if (average >= 60) return "C"; else if (average >= 50) return "D"; else return "F"; } }
