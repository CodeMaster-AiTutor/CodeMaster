Encapsulation

What is Encapsulation?

Encapsulation is one of the four fundamental concepts of Object-Oriented Programming (OOP). It refers to the bundling of data (fields) and methods that operate on that data into a single unit, called a class. More importantly, it restricts direct access to some of an object's components, which is a means of preventing accidental interference and misuse of the methods and data. This controlled access is typically achieved by making fields private and exposing them only through public methods known as getters and setters.

  • Make fields private to hide them from the outside world.
  • Provide public getters and setters to control how data is accessed and modified.

The Problem Without Encapsulation

When fields are public, any part of your program can change them to any value, valid or not. For example, a student's age could be set to a negative number, or their name could be set to an empty string. This lack of control leads to inconsistent data and bugs that are hard to track down. Without encapsulation, the class cannot guarantee the integrity of its own state.

public class Student { public String name; public int age; public double marks; } Student s = new Student(); s.age = -5; s.marks = 150; s.name = "";

In the example above, the `Student` object is left in a corrupted state because invalid data was assigned directly. There is no protection mechanism to stop this.

With Encapsulation

By making fields private and using public setter methods, the class takes control over its own data. The setter method acts as a gatekeeper, checking if the new value is valid before assigning it to the field. If the value is invalid, the setter can reject it, throw an error, or assign a default value. This ensures that the object always remains in a valid and consistent state.

public class Student { private String name; private int age; private double marks; public String getName() { return name; } public int getAge() { return age; } public double getMarks() { return marks; } public void setName(String name) { if (name == null || name.trim().isEmpty()) { System.out.println("Name cannot be empty."); return; } this.name = name; } public void setAge(int age) { if (age < 1 || age > 120) { System.out.println("Invalid age: " + age); return; } this.age = age; } public void setMarks(double marks) { if (marks < 0 || marks > 100) { System.out.println("Marks must be between 0 and 100."); return; } this.marks = marks; } }

Notice how the logic for validation lives inside the class itself. This means you don't have to repeat validation checks every time you use the object in different parts of your code.

Getter and Setter Naming Convention

Java follows a strict naming convention for getters and setters (JavaBeans standard). This consistency allows frameworks and libraries to interact with your objects automatically. Getters start with `get` followed by the capitalized field name, while setters start with `set`. For boolean fields, the getter often starts with `is` instead of `get` to read more naturally.

Field Getter Setter
name getName() setName()
age getAge() setAge()
active (boolean) isActive() setActive()

Read-Only Fields

Sometimes you want a field to be set once (usually in the constructor) and never changed again. You can achieve this by providing a public getter method but omitting the setter method. This effectively makes the field "read-only" to the outside world, while keeping it private internally. This pattern is crucial for creating immutable objects, which are safer to use in multi-threaded environments.

public class Student { private int id; public Student(int id) { this.id = id; } public int getId() { return id; } }

Encapsulation with Constructors

Constructors are the first line of defense for your object's integrity. Instead of assigning parameters directly to fields, a constructor should often call the class's setter methods. This ensures that validation logic runs immediately when the object is created, preventing it from ever existing in an invalid state. If you bypass setters in the constructor, you might accidentally initialize an object with bad data.

public class Student { private int id; private String name; private int age; private double marks; public Student(int id, String name, int age, double marks) { this.id = id; setName(name); setAge(age); setMarks(marks); } public int getId() { return id; } public String getName() { return name; } public int getAge() { return age; } public double getMarks() { return marks; } public void setName(String name) { if (name == null || name.trim().isEmpty()) { System.out.println("Invalid name."); return; } this.name = name; } public void setAge(int age) { if (age < 1 || age > 120) { System.out.println("Invalid age."); return; } this.age = age; } public void setMarks(double marks) { if (marks < 0 || marks > 100) { System.out.println("Invalid marks."); return; } this.marks = marks; } public String getGrade() { if (marks >= 90) return "A"; if (marks >= 75) return "B"; if (marks >= 60) return "C"; return "F"; } @Override public String toString() { return String.format("[%d] %-12s Age: %-4d Marks: %-6.1f Grade: %s", id, name, age, marks, getGrade()); } }

Access Modifiers Summary

Access modifiers determine the visibility of classes, fields, and methods. `private` restricts access to the defining class only, which is the cornerstone of encapsulation. `public` allows access from anywhere, making it suitable for methods that define the object's interface. `protected` and default (package-private) offer intermediate levels of visibility useful for inheritance and package-level organization.

Modifier Same Class Same Package Subclass Anywhere
private ✅ ❌ ❌ ❌
(default) ✅ ✅ ❌ ❌
protected ✅ ✅ ✅ ❌
public ✅ ✅ ✅ ✅

For strict encapsulation: fields should almost always be private, while methods intended for external use are public.

Private Helper Methods

Not all methods in a class need to be exposed to the outside world. If a method is only used internally by other methods of the same class, it should be marked as `private`. These "helper" methods decompose complex logic into smaller, manageable pieces without cluttering the public API. This keeps the class interface clean and easy to understand for other developers.

public class Student { private double marks; public void setMarks(double marks) { if (isValidMarks(marks)) this.marks = marks; else System.out.println("Invalid marks."); } private boolean isValidMarks(double marks) { return marks >= 0 && marks <= 100; } }

Full Example: BankAccount

This example demonstrates a fully encapsulated class. The `balance` field is private, protecting it from arbitrary modification. Money can only be added or removed via `deposit` and `withdraw` methods, which enforce rules like preventing negative amounts or overdrafts. Even the constructor uses these methods to ensure the initial state is valid.

public class BankAccount { private int accountNo; private String owner; private double balance; public BankAccount(int accountNo, String owner, double initialDeposit) { this.accountNo = accountNo; setOwner(owner); deposit(initialDeposit); } public int getAccountNo() { return accountNo; } public String getOwner() { return owner; } public double getBalance() { return balance; } public void setOwner(String owner) { if (owner == null || owner.trim().isEmpty()) { System.out.println("Owner name cannot be empty."); return; } this.owner = owner; } public void deposit(double amount) { if (!isValidAmount(amount)) return; balance += amount; System.out.printf("Deposited: $%.2f | Balance: $%.2f%n", amount, balance); } public void withdraw(double amount) { if (!isValidAmount(amount)) return; if (amount > balance) { System.out.println("Insufficient funds."); return; } balance -= amount; System.out.printf("Withdrew: $%.2f | Balance: $%.2f%n", amount, balance); } private boolean isValidAmount(double amount) { if (amount <= 0) { System.out.println("Amount must be greater than zero."); return false; } return true; } @Override public String toString() { return String.format("Acc#%d | Owner: %s | Balance: $%.2f", accountNo, owner, balance); } }

Benefits of Encapsulation

Encapsulation offers several long-term benefits for software development. It protects data from corruption, makes code easier to maintain by localizing validation logic, and allows implementation details to change without affecting other parts of the system. For example, you could change how `balance` is stored (e.g., from double to BigDecimal) without changing how external code calls `getBalance()`.

Benefit Explanation
Data protection Invalid values are rejected
Flexibility Change internal logic without breaking outside code
Readability Clear what can and cannot be accessed
Maintainability One place to update validation rules

Common Mistakes

A common mistake is creating public fields for convenience, which breaks encapsulation immediately. Another is writing "lazy" setters that just assign values without any validation, missing the point of having a setter. Finally, failing to use setters inside constructors can lead to objects that start their life with invalid data.

public double balance; private double balance; public void setAge(int age) { this.age = age; } public void setAge(int age) { if (age > 0 && age < 120) this.age = age; } public Student(String name, int age) { this.name = name; this.age = age; } public Student(String name, int age) { setName(name); setAge(age); }
Exam Point: Identify the mistake in each example.

Practice Exercises

These exercises will help you practice designing classes that protect their internal state. Start by identifying which fields need protection and what rules should apply to them. Then, implement the class with private fields and public methods that enforce those rules. Testing your class with both valid and invalid data is key to verifying your encapsulation logic.

  • Create a BankAccount class with private balance and deposit/withdraw validation.
  • Create a Person class with private name, age, email and validate age and email.
  • Create a Temperature class with private celsius and a getFahrenheit() method.
  • Show why private fields are safer than public fields.
  • Create a Product with read-only id and settable price with validation.
  • Create a BankAccount with constructor + setters and a private helper method.
  • Create a Circle with private radius and public area/perimeter methods.
  • Create an Employee with salary and a raiseSalary method with limits.
  • Create a Hospital patient class with validated blood type and age.
  • Create a Vehicle class with speed limits and accelerate/brake methods.
  • Refactor a class to add encapsulation and explain the benefits.
